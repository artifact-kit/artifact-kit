# Route-Aware BBox Segmentation Proposal

Linear: ART-10

## Problem

The bbox review workflow currently treats bounding boxes mostly as visual segmentation. That is not enough for PPT reconstruction.

The same visual region should be boxed differently depending on how it will be implemented:

- If the region will become one final image or one embedded SVG image, one bbox for the whole asset is enough.
- If the region should become editable PPT elements, it needs child bboxes for each editable unit.

The current `iot-innovation-project` data shows the gap:

- `full-page-final.json` contains visual boxes and hierarchy, but no route/editability fields.
- `reconstruction-manifest.json` adds `strategy` later through `scripts/build-reconstruction-inputs.mjs`.
- That script classifies based on `kind`, id special cases, and broad heuristics. This is useful, but it is too late: human bbox review already happened without seeing the intended route.

This creates two failure modes:

- Too fine: a complex illustration can be split into many internal boxes even if the final implementation is one generated/source raster asset.
- Too coarse: a diagram row can be one group bbox even if each icon/label should remain independently editable.

## Design Goal

Move reconstruction intent into the bbox review data before human review.

The bbox stage should answer two questions for each element:

1. What visual area is this?
2. How will implementation place it in the PPT?

The second answer determines bbox granularity.

## Recommended Schema

Extend each bbox element with optional reconstruction fields:

```ts
type ReconstructionRoute =
  | 'layout-only'
  | 'native-shape'
  | 'native-text'
  | 'svg-image'
  | 'editable-vector'
  | 'imagegen'
  | 'source-raster'
  | 'drawio-svg'

type Editability =
  | 'none'
  | 'asset'
  | 'group'
  | 'element'

interface ElementNode {
  id: string
  parentId?: string
  label: string
  kind: ElementKind
  bbox: BBox
  description?: string
  reviewStatus?: ReviewStatus

  route?: ReconstructionRoute
  editability?: Editability
  renderRole?: 'render' | 'layout' | 'context'
  routeReason?: string
  childrenPolicy?: 'none' | 'optional' | 'required'
}
```

Field meaning:

- `route`: intended reconstruction method.
- `editability`: expected PPT editability level.
- `renderRole`:
  - `render`: this bbox produces an output element.
  - `layout`: this bbox is only for alignment/grouping.
  - `context`: this bbox gives review context but is not directly rendered.
- `childrenPolicy`:
  - `none`: do not split unless implementation changes.
  - `optional`: child boxes may help but are not required.
  - `required`: implementation needs child boxes.

## Route Definitions

- `layout-only`: grouping/alignment bbox, not directly drawn.
- `native-shape`: PPT primitive shape, such as rect, roundRect, ellipse, line, arrow, footer band.
- `native-text`: PPT text box.
- `svg-image`: accepted SVG inserted with core `slide.addImage({ path: svgPath })`; vector-scalable but not path-editable.
- `editable-vector`: vector visual that should become editable PPT shapes/custom geometry; requires child or path-level planning.
- `imagegen`: final raster generated by image model.
- `source-raster`: source crop or user-provided bitmap is the intended final asset.
- `drawio-svg`: structured diagram represented as draw.io XML, exported to SVG, then embedded as SVG image.

## Granularity Rules

Use this decision test when creating or reviewing bboxes:

> Will implementation place exactly one thing here?

If yes, one bbox is enough.

If no, split into the things implementation will place.

Specific rules:

- For `imagegen`, `source-raster`, and `svg-image`, use one bbox for the final asset unless subparts will be validated or edited independently.
- For `native-text`, create one bbox per text block that will be placed as one text box.
- For `native-shape`, create one bbox per primitive/card/container/line that will be placed.
- For `editable-vector`, create child bboxes for useful editable units, such as icon, label, connector, node, or repeated subcomponent.
- For `layout-only`, keep the parent bbox but do not count it as an implementation element.
- Parent group bboxes and child render bboxes can coexist. The parent should use `renderRole: 'layout'` or `context`.

## Example Fixes

### Top-right illustration

If final route is one generated image:

```json
{
  "id": "top_right_visual",
  "route": "imagegen",
  "editability": "none",
  "renderRole": "render",
  "childrenPolicy": "none"
}
```

Then internal boxes like `city_skyline` and `network_pattern` should be removed or marked:

```json
{
  "id": "city_skyline",
  "route": "imagegen",
  "renderRole": "context"
}
```

If final route is separate SVG/image assets, keep sub-bboxes only for assets that will be separately generated and placed.

### Sensing/service icon rows

If they should remain editable:

```json
{
  "id": "system_sensing_icons",
  "route": "layout-only",
  "editability": "group",
  "renderRole": "layout",
  "childrenPolicy": "required"
}
```

Then add child boxes:

```json
{
  "id": "system_sensing_temperature_icon",
  "parentId": "system_sensing_icons",
  "route": "editable-vector",
  "editability": "element",
  "renderRole": "render"
}
```

and a separate text box:

```json
{
  "id": "system_sensing_temperature_label",
  "parentId": "system_sensing_icons",
  "route": "native-text",
  "editability": "element",
  "renderRole": "render"
}
```

If the row is acceptable as one vector image, keep one bbox:

```json
{
  "id": "system_sensing_icons",
  "route": "svg-image",
  "editability": "asset",
  "renderRole": "render",
  "childrenPolicy": "none"
}
```

The key is that the route makes the tradeoff explicit.

## Workflow Change

Current bbox workflow:

1. VLM/agent creates an initial element list with route/editability guesses.
2. Agent applies granularity rules:
   - collapse boxes where final route is one asset
   - split boxes where route requires editable children
3. Agent writes an initial bbox JSON file that can be uploaded into the standalone browser workbench.
4. Human opens the workbench, uploads the local source image and initial bbox JSON, then reviews bbox geometry and route/editability fields in the browser.
5. Human or agent can change route if the implementation intent is wrong.
6. The workbench downloads `<input-file>.final.json`.
7. The final bbox JSON becomes the source for reconstruction; no separate heuristic classification pass should be required.

There is no server-side session, MCP session, API upload, or persistent storage in the default workflow. The source image and bbox JSON stay local to the browser, and save/export is a file download.

## Accepted Initial JSON Shapes

The standalone loader accepts several shapes for compatibility:

- raw bbox review data: `{ imageAssetId, image, elements }`
- session envelope: `{ workbenchType: "bbox-review", data, assets }`
- element manifest: `{ source, image, boxes }`
- project fixture: `{ sourceImagePath, manifest: { image, boxes }, review }`

New route-aware reconstruction work should prefer raw bbox review data:

```json
{
  "title": "IoT Innovation Project bbox review",
  "imageAssetId": "source",
  "image": {
    "width": 1672,
    "height": 941
  },
  "activeElementId": "canvas",
  "instructions": "Review bbox geometry and route-aware reconstruction fields.",
  "status": "needs-human",
  "elements": [
    {
      "id": "canvas",
      "label": "Full slide canvas",
      "kind": "canvas",
      "bbox": { "x": 0, "y": 0, "w": 1672, "h": 941 },
      "route": "layout-only",
      "editability": "group",
      "renderRole": "layout",
      "childrenPolicy": "required",
      "granularityFeedback": "ok",
      "routeReason": "Whole-slide alignment reference.",
      "reviewStatus": "pending"
    }
  ]
}
```

## Workbench Implementation

Implemented UI behavior:

- Show `route`, `editability`, `renderRole`, `childrenPolicy`, and `granularityFeedback` in the right-side review pane.
- Let the reviewer edit those fields directly with dropdown controls.
- Let the reviewer edit `routeReason` and `notes` as text.
- Visually distinguish layout/context boxes from render boxes.
- Run as a standalone browser app: upload a local source image and local initial bbox JSON, then download reviewed JSON.

Still useful future enhancement:

- Add a filter for `renderRole`, so humans can focus on boxes that will actually be placed.

Granularity feedback should be explicit:

- `ok`: bbox granularity matches the reconstruction plan.
- `too-coarse`: this bbox should be split into child elements.
- `too-fine`: this bbox should be merged into a larger final asset/group.

If the reviewer marks `too-coarse` or `too-fine`, completing the area should set `reviewStatus: 'needs-agent'` rather than `accepted`. The reviewer should use `notes` to describe the desired split/merge.

Schema status:

- The optional fields are in `elementNodeSchema` in `packages/deckkit-workbench/src/lib/workbench-registry.ts`.
- Keep them optional for backward compatibility with old manifests.

## Build Script Changes

`examples/iot-innovation-project-bbox-work/scripts/build-reconstruction-inputs.mjs` should prefer explicit route fields:

```js
function classify(element) {
  if (element.route) return routeToStrategy(element)
  return legacyKindBasedClassification(element)
}
```

Mapping:

- `layout-only` -> `layout-reference`
- `native-shape` -> `native-shape`
- `native-text` -> `native-text`
- `svg-image` -> `svg-image` or current vector/image bucket
- `editable-vector` -> `editable-vector` or current vector bucket
- `imagegen` -> `raster-image`
- `source-raster` -> `raster-image`
- `drawio-svg` -> `svg-image`

This keeps existing data working while allowing new manifests to be explicit.

## Rollout Plan

1. Update docs/lessons with the route-aware rule. Done.
2. Add optional route/editability fields to workbench schema. Done.
3. Display and edit route/editability in `BBoxReviewWorkbench`. Done.
4. Convert the workbench into a standalone browser tool that loads local image + JSON and downloads reviewed JSON. Done.

8. Once validated, use the same schema for future examples.

## Non-Goals

- Do not make route choice fully automatic yet.
- Do not require every old bbox manifest to be migrated immediately.
- Do not reintroduce server/session persistence for the default review workflow unless there is a clear need.
- Do not force all vector assets to become editable. `svg-image` is a valid final route.

## Recommendation

Implement this incrementally as schema-first, UI-light.

The most valuable immediate change is not a complex workbench feature. It is making every bbox carry enough reconstruction intent that the agent, human reviewer, and later build scripts all agree on whether the bbox is a final asset, a layout reference, or an editable child element.
